# Fire HD 8 卓上スマートディスプレイ 設計書

日付: 2026-11-12 / 状態: レビュー待ち
前版（Pi Zero 2 W + HDMIタッチ + pygame, `2026-11-12-pi-desk-device-design.md`）を置き換える。Pi は今回使わない。

## 1. 目的
使わなくなった Fire HD 8（第12世代・2022年、Fire OS 8.3.3.3）を、Echo Show のような卓上の専用端末に作り替える。余計な機能を止め、必要な機能だけを自作アプリで載せる。

## 2. 前提と制約（調査結果）
- OSの入れ替え（カスタムROM）は不可。2020年以降のFireタブレットはブートローダーを解除できない。
- Fire OSのまま、不要アプリの停止・標準ホームの無効化・自動更新の停止を行う。Fire OS 8 ではシステム権限の抜け道が必要で、8.3.3.8 で塞がれたと報告されている。8.3.3.3 は未修正とされる。
- **2026-11-12 更新: 端末は自動更新で 8.3.3.8 になった。** システム権限の抜け道は使えない前提に変更する。8.3.3.8 で使う手段は、(a) PCからのコマンドによる不要アプリの停止、(b) Fire Toolbox のカスタムランチャー機能（回避策方式）。標準ホームの完全な無効化、ロック画面広告の停止、自動更新の停止はできない前提で設計する。
- 8.3.3.8 は現時点の最新版（2025年12月公開）。今後の更新で (a)(b) が塞がれる可能性は残る。
- 8.3.3.8 向けのroot手法の報告はあるが、今回は使わない（必須ではなく、リスクが高い）。
- 標準モデルはRAM 2GB。軽量化後に実用的な速さになるかは未検証（§9のフェーズ0で確かめる）。

## 3. 機能範囲
含む:
- ポモドーロタイマー（作業25分/休憩5分、4回ごとに長休憩15分。時間は設定可）
- 時計・日付
- 天気（現在＋数時間〜翌日）
- Googleカレンダーの予定表示（読み取り専用）と予定前通知（既定10分前）
- 通知音（タブレットのスピーカー）と画面の色変化
- タッチ操作のカード型ホーム画面とタイマー画面
- 無操作時の減光

含まない（今回作らない）: 音声操作、室温・湿度、作業ログ、カレンダーへの書き込み、root化。
室温・湿度はPi案から外れた。必要になれば無線センサーを後から足す。

## 4. 構成
```
[Fire HD 8]
  軽量化済み Fire OS（不要アプリ停止、自動更新停止、ホーム差し替え）
  └ キオスク表示アプリ（全画面ブラウザ、起動時に自動表示）
      └ ダッシュボード Webアプリ（HTML/CSS/JS、ビルド工程なし）
            ├ 天気: Open-Meteo を直接取得
            └ 予定: カレンダー中継（Google Apps Script）から JSON を取得
[ユーザーのGoogleアカウント]
  └ カレンダー中継スクリプト（直近の予定だけを返す。秘密のトークン付きURL）
```
- 中継が必要な理由: ブラウザのアプリからは、Googleカレンダーの非公開iCal URLを直接読めない見込み（クロスオリジン制限）。計画段階で実際に確かめ、直接読めるなら中継は省く。
- Webアプリの置き場所（タブレット内のローカルファイルか、静的ホスティングか）と、キオスク表示アプリの選定（OSSを優先）は計画段階で実機確認して決める。

## 5. Webアプリの内部構成
```
core/timer.js      ポモドーロ状態機械（時計を外から注入、画面に依存しない）
core/schedule.js   予定の整形と「次の通知時刻」の計算
services/weather.js   Open-Meteo取得、変換、localStorageにキャッシュ
services/calendar.js  中継から取得、キャッシュ
ui/home.js, ui/timer.js   画面（カード表示、タッチボタン）
ui/notify.js       通知音と画面の色変化
ui/settings.js     設定画面（緯度経度、各時間、中継URL）。値は端末のlocalStorageに保存
```
- 2026-11-12 計画段階の決定: 設定は `config.js` ファイルではなく端末上の設定画面で入力する。秘密の中継URLがリポジトリに入らないため、Webアプリは静的ホスティング（GitHub Pages）に置ける。ES Modulesは `file://` では読み込めないため、ローカルファイル方式は採らない。
- カレンダー中継は Apps Script の CalendarApp で予定を取得する（繰り返し予定は展開済みで返る）。iCalの解析は不要になった。
- タイマーは終了予定時刻を保存し、画面が再読み込みされても残り時間を復元する。
- 天気と予定は30分ごとに更新する。

## 6. エラー処理
- 天気・予定の取得失敗: 前回値を最終更新時刻つきで表示。タイマーと時計は止めない。
- Wi-Fi断中もタイマーは動く。
- 中継URLのトークンは秘密情報。リポジトリに入れず、画面にもログにも出さない。

## 7. 端末の運用
- 常時給電によるバッテリー劣化・膨張への対策を入れる（充電上限の制御が可能か、またはスマートプラグ等での間欠充電）。方式は計画段階で決める。
- 自動更新は止められないため、更新後に設定が戻っていないかを確認する手順を運用に入れる（停止したアプリの一覧を再適用できるスクリプトを用意する）。
- ロック画面は、キオスク表示アプリの「画面を消さない」設定で通常は通らない運用にする。
- 軽量化で止めたアプリは一覧に記録し、元に戻せるようにする。

## 8. 参考にするOSS・ツール（コードは流用しない／ツールは利用のみ）
Fire Toolbox（軽量化）、Fire-Tools、View Assist（画面構成の参考）。

## 9. 進め方と検証（正しさの示し方）
**フェーズ0: 軽量化の検証（最初に行う。ユーザーが実機で実施）**
1. PCとUSB接続して軽量化（不要アプリ停止 → カスタムランチャー導入）。8.3.3.8 では自動更新停止は行わない。
2. 判定: テスト用のWebページ（時計が毎秒更新、ボタン付き）を全画面表示し、(a)タッチの反応が体感で即時、(b)3時間つけっぱなしで固まらない、(c)再起動後も設定が保たれる。3点を満たせば続行。満たさなければ中止してPi案に戻す。

**フェーズ1: Webアプリ**
1. 自動テスト（PC上、`node --test`）: 偽の時計で状態機械を検証（25分で休憩へ、4回目で長休憩、一時停止/再開/リセット、再読み込み後の復元）。予定の整形と通知時刻（終日・タイムゾーン違い・繰り返し展開済みデータ）。天気の変換と失敗時のキャッシュ表示。
2. PCのブラウザで 1280×800 の画面を表示し、スクリーンショットで目視確認。

**フェーズ2: 実機への組み込み**
手順書に沿って、起動時の自動表示、通知音、減光、Wi-Fi断、24時間連続表示をユーザーが確認する。

## 10. 自己レビュー結果
プレースホルダなし。未確定の3点（iCal直接取得の可否、キオスク表示アプリ、充電制御の方式）は計画段階の確認事項として明記した。最大の不確実性は軽量化後の速さで、フェーズ0で先に判定する。
